# Changelog

All notable changes to Hydrogen are listed here. Versions follow [Semantic Versioning](https://semver.org); while the version is `0.x`, a minor bump can contain breaking changes.

## Unreleased

### Added

- Meters can be read at a past server time on the server: `PlayerMeter:getAt(player, serverTime)` and `StateMeter:getAt(serverTime)` return the value from the segment that was in force then (clamped to its range), or `nil` when the time is older than the new `history` option. Paired with `Guards.timestamp()`, a client action is judged at the moment the player acted rather than when the request arrived, which replaces flat tolerances on `get()`. `history = seconds` is opt-in: without it nothing is kept and `getAt` errors with the option to add. Past segments are kept only on writes, pruned to the window on each write and capped at 128 per meter per player, and dropped when a player leaves. `docs/ai/state.md` has a "Judge an action at the moment the player acted" recipe.
- `MeterOptions` and `PlayerMeterOptions` take `history: number?`.

### Fixed

- Strict type errors in game code with the luau-lsp version `create_hydrogen` pins (1.70.1), which failed a new project's own type check:
  - `app:start()` and `app:stop()` in the generated `Main` scripts no longer fail with "Expected this to be exactly ... but got 'App'". Every `App` method now names its `self` type, instead of each method inferring a slightly different one.
  - Fields declared with the `read` modifier (`scope.alive`, `scope.name`, `timer.active`, `connection.Connected`, `component.tag`, `config.values`, and others) are visible again. That luau-lsp can't parse `read`, so it reported "Key not found". The modifier is gone from every public type; the fields are still read-only by contract.
  - Literal unions: `network.md` and the README show how to keep `"M1" | "M2"` instead of `string` in handlers (annotate the network object, cast the constructor). GreenTea's generic signatures can't keep them on their own.
- CI type-checks `test/Types/`, strict game code calling Hydrogen, with that luau-lsp version, so these can't come back.

## 0.5.3

### Fixed

- `Hydrogen.Component` no longer errors in `start` in a live game. The signal source read a `root` field on the real `CollectionService`, which throws ("root is not a valid member of CollectionService") and stopped the whole app's boot on server and client. Tests used a table stand-in, so they never hit it; a new test uses a real Instance.

## 0.5.2

### Added

- `Hydrogen.Guards.timestamp(options?)`: drops a message whose `Clock.serverNow()` stamp is from the future, or older than the sender's ping (capped by `maxPing`) plus `tolerance`, so a client can't backdate an action. `Guards.ping(player)` reads `Player:GetNetworkPing()`, and `Guards.configure` takes `ping` (a replacement source, e.g. for tests) and `maxPing` (the default cap, 1 second). New type `Hydrogen.TimestampOptions`.

## 0.5.1

### Added

- `Hydrogen.Clock.serverNow()`: the server's clock, shared by the server and every client (`workspace:GetServerTimeNow()` in a game), for timestamps one side sends and the other compares. The fake clock drives it from a new `serverNow` option (default: the `time` option), and `fake:setServerOffset(seconds, player?)` skews it for one loopback client, or all of them, to test latency and clock skew.
- Input buffering on button actions: `context:button(name, bindings, { buffer = seconds })` remembers each press for `buffer` seconds (timed with `Hydrogen.Clock`), and `action:consumeBuffered(): boolean` takes it once, so a combo press made during recovery fires when the recovery ends. Disabling the action's context clears the buffered press; sunk presses are never buffered. No per-frame work.
- Meters in `Hydrogen.State`: `State.meter(name, options)` and `State.playerMeter(name, options)` for numbers that move at a steady rate between a min and a max (stamina, mana, posture, hunger, temperature). The state is a segment `(value, rate, min, max, at)` replicated only when it jumps (`set`, `add`, `setRate`, `setRange`), with `at` in `Clock.serverNow()` time; `get()` on either side extrapolates to now and clamps, so time passing sends nothing and costs nothing. `getRate`, `getRange`, `observe` (on changes only) and `onLimit` (called when the value reaches min or max, from one `Clock.delay` rescheduled on change). Per-player meters take `visibleTo`, have `observeAll`, and with `predict = true` let the owning client `predictRate` / `predictAdd` its own view until the next server update replaces it or `predictTimeout` passes; the server can `sync(player)` to correct a prediction at once. Late joiners get the current segment; a client whose clock is behind holds the value instead of running it backwards. Types `StateMeter`, `PlayerMeter`, `MeterOptions`, `PlayerMeterOptions` and `MeterLimit`.
- `Hydrogen.Teleport`, server-only teleports that hand off `Hydrogen.Data` cleanly. `Teleport.send(players, placeId, options?)` runs `Teleport.onHandOff` callbacks, saves and releases every `Data.player` store the players are in, and only then calls `TeleportAsync`, so the destination's load never waits for this server's lock. `Failure`, `Flooded` (15 s) and `TeleportAsync` errors are retried with backoff up to `attempts` (3); players who stay (failed, `TimedOut` after `timeout`, shutdown) get their data back under the same lock, keeping changes made meanwhile when the stored record is unchanged, or the store's `onLoadFailed` runs if it can't be taken back. Parties retry only failed members, into the same reserved server. A second send for a player answers `Busy`; players who leave mid-teleport are handled; `app:stop()` ends retries. Options: `serverId`, `reservedCode`, `reserveServer`, `data`, `attempts`, `timeout`. The result lists `teleported`, `failed` (with a reason and message), `attempts` and `reservedCode`.
- `Teleport.ticket(name, schema)`: typed teleport data. `ticket:send(players, placeId, value, options?)` validates and sends it; `ticket:read(player)` reads it on arrival through the schema (untrusted: it passes through the client). Also `Teleport.joinData`, `Teleport.reserve`, `Teleport.configure` and `Teleport.fakeService()`, a stand-in TeleportService for tests (`failNext`, `errorNext`, `hold`/`complete`/`fail`, `arrive`, `requests`).
- `Hydrogen.Messaging`, typed MessagingService topics. `Messaging.topic(name, schema, { ignoreSelf? })` gives `publish(value)`, which errors at once on a schema failure, a value JSON can't hold or a message over 1000 bytes, waits for the per-server publish budget (600 + 240 per player per minute) and retries failures, and `subscribe(fn)`, which delivers frozen values with `{ sent, serverId, fromThisServer }` and drops messages that fail the schema with a rate-limited warning. Nothing touches MessagingService until a topic is used; subscribers to a topic share one subscription, made in the background and retried. `app:stop()` drops every subscription; `scope:add(topic:subscribe(fn))` ties one to a scope. `Messaging.configure`, `Messaging.serverId()` and `Messaging.memoryBus()`, an in-memory MessagingService for tests.
- Types `TeleportResult`, `TeleportFailure`, `TeleportFailReason`, `TeleportSendOptions`, `TeleportRequest`, `TeleportAccepted`, `TeleportBackend`, `TeleportConfig`, `TeleportTicket<T>`, `FakeTeleportService`, `MessagingTopic<T>`, `MessagingTopicOptions`, `MessageInfo`, `MessagingBackend`, `MessagingMessage`, `MessagingConfig` and `MessagingMemoryBus`.
- `Hydrogen.Data`: player stores can be handed off for a teleport (internal, used by `Hydrogen.Teleport`): saved and released while still readable here, then either dropped when the player leaves or taken back. During a hand-off `isLoaded` is false, `update` changes memory only, `updateOnce` returns `"failed"` and `transaction` errors.

### Changed

- The docs now say to register network listeners (`:On`, `:Use`) in `init`, everywhere. The network starts between `init` and `start`, and a client handles the events queued for it right then, so a listener added in `start` could miss them silently. `systems.md`, `network.md`, `scope.md`, the README and the `create_hydrogen` example systems said `start`; `testing.md` and `guards.md` already said `init`.
- `create_hydrogen` 0.1.2: new projects pin Hydrogen `^0.5.1`, and the example systems register their listeners in `init`.

### Fixed

- Docs: `component.md` no longer calls character hooks "planned"; `data.md`'s receipt recipe points to `Hydrogen.Receipts.fromData`; `input.md` calls a clientFunction with `:Fire`, not `:Invoke`; `clock.md`'s quick start no longer uses the `Clock.wait` loop `scheduler.md` warns against.
- Docs: every Luau example in `README.md` and `docs/ai/*.md` is now checked by the test suite (and CI): it must compile, and every `Hydrogen.*` name it uses must exist. Three examples that didn't compile were fixed (the middleware shape, and two network modules that mixed a `local` with table fields).
- Docs: a recipe for testing hit detection under Lune, where spatial queries don't exist: one query system, replaced in tests (`testing.md`, README).
- `Hydrogen.Data`: a release (save on leave) whose first write landed but reported an error was retried, found its own lock gone and warned that another server took it; the retry now completes the release.
- `create_hydrogen` 0.1.1: on macOS and Linux, a missing git, Rokit or pesde is reported with its install instructions. 0.1.0 only recognized Windows' "program not found" and treated the tool as installed but failing.

## 0.5.0

### Added

- `Hydrogen.test(options?, fn)`: one call per test. It opens a loopback, installs a fake clock, builds and starts an app from `systems`, applies `replace` fakes, joins `players` (passed to `fn` after the harness), runs `fn`, and always tears down: stops the app, closes the loopback and restores the clock, even when `fn` or the boot errors. `start = false` leaves setup to the test (`t:add`, `t:replace`, `t:join`, `t:start`).
- `Hydrogen.harness(options?)`: the same harness without the function, for frameworks with setup and teardown hooks; call `t:close()`. A harness left open is closed, with a warning, when the next one opens.
- Expectations on what network objects delivered: `t:expect(object)` with `fired`, `firedTo`, `firedBy`, `notFired`, `firedTimes`, `called`, `calledBy`, `returned`, `notCalled`, `calledTimes` and `deliveries`, plus `t:expectNothingFired()`. Arguments compare by value, `t.any` matches any value, and a failure errors at the test line with what was delivered instead. They work with frktest, TestEZ, Jest-Lua or no framework.
- Warning capture in the harness: `t:expectWarning(text)`, `t:expectNoWarnings()` and `t:warnings()`. Warnings no expectation matched are printed when the test ends.
- `Hydrogen.Clock`: `now`, `time`, `wait`, `delay`, `cancel` and `heartbeat`, which are the built-ins in a game, and `Clock.fake(options?)`, a controllable clock (`advance`, `next`, `pending`, `restore`). The harness installs one, so timeouts, rate-limit refills and timers in systems run deterministically with `t:advance(seconds)`.
- `src/Testing/Lune.luau`: the Lune runtime Hydrogen's tests run on, shipped so games can run system tests under Lune. `Lune.install()` sets the Roblox globals; `Lune.require` loads modules with Roblox require rules, `.luaurc` aliases, pesde package links and `require(script...)`, and names them like Roblox full names so inferred system ids match Studio.
- Types `Harness`, `TestOptions`, `Expectation`, `Delivery`, `FakeClock` and `FakeClockOptions`.
- `Hydrogen.Scope` and the `Scope` type: cleanup tied to lifetimes. A scope tracks functions, threads, connections, Instances, other scopes and objects with `Destroy`, `Disconnect` or `cancel`, and cleans them newest first; a task that errors is warned about and the rest still run. `scope:connect`, `scope:spawn`, `scope:delay` and `scope:child` create and track in one call. A destroyed scope cleans anything added to it straight away.
- System and player scopes: `Hydrogen.Scope.of(system)` and `Hydrogen.Scope.of(system, player)`, created on first use and the same from anywhere. Player scopes are destroyed right after the system's `playerRemoving` for that player (reverse dependency order); system scopes right after the system's `stop` hook on `app:stop()`, or when the boot fails. Systems that never ask create no scope, and hooks are called as before.
- `Hydrogen.Data`: session-locked DataStore persistence. `Data.player(name, options)` is a system that loads each player in `playerAdded` (so systems that `use` it see loaded data in their own `playerAdded`), saves and releases them in `playerRemoving`, autosaves, and saves everything on `stop`. `Data.store(name, options)` does the same for string keys with `load` / `unload`. Stores have `get`, `find`, `isLoaded`, `update` (copy, validate, commit; return `false` to abort), `save`, `view`, `changed`, `transaction` (several keys all-or-nothing, saved with a two-phase commit), `updateOnce` (once per id, recorded atomically with the change, for purchase receipts) and `waitForLoad`. An `update` called inside another update's callback for the same key changes that callback's pending copy. Includes session locking with abandoned-lock takeover, GreenTea schema validation, template reconciliation, versioned migrations with backwards-compatible steps, retries with exponential backoff, request-budget waiting and `BindToClose` handling. Data is deep-frozen.
- `Data.memory()`: an in-memory backend with failure injection, budgets, latency and `peek`, used automatically under Lune and `Hydrogen.loopback()`. `Data.useBackend(backend)` and the `backend` option swap backends; `Data.dataStores()` is the Roblox one.
- `Hydrogen.PlayerState`: per-player state created on join and removed on leave in dependency order. `PlayerState.new(name, { data, runtime, replicate })` takes saved fields from a Data store, runtime-only fields with defaults, and one word per replicated field (`"owner"` or `"everyone"`). Assigning a field validates it, saves it through the store and replicates it at the end of the frame. `get`, `find`, `update`, `changed` and, for tests, `replica`.
- Types: `PlayerStore<T>`, `KeyStore<T>`, `DataBackend`, `MemoryBackend`, `UpdateOnceResult`, `PlayerState<S>`.
- `Hydrogen.State`: server-authoritative state replicated to clients, defined in shared modules. `State.value`, `State.map` and `State.list` for global state; `State.playerValue`, `State.playerMap` and `State.playerList` for per-player state seen by its owner or, with `visibleTo = "everyone"`, by every player, with `observeAll` to watch every player's value; `State.computed` for derived state. Writes are checked against a GreenTea schema and coalesced into one message per changed state per frame (`State.flush()` sends now). Maps send key diffs and lists send operations. Joining players get a snapshot in the ready handshake, and departed players' state is dropped from clients. Options: `encode`, `serializer`. Under `Hydrogen.loopback()` each fake client has its own replica; `State.reset()` clears everything between tests.
- `Hydrogen.Receipts`, a system that owns `MarketplaceService.ProcessReceipt` and grants each developer product purchase once. Systems register handlers with `Receipts.product(id, handler)` or `Receipts.products({ ... })`. A receipt waits for its player to load, runs one at a time per player, and is answered `PurchaseGranted` only after the store reports the grant saved. Handler errors, a `false` return, unknown products (warned), players who leave or never load, failed saves (retried first) and shutdown answer `NotProcessedYet`. A leaving player's grant in progress finishes before later `playerRemoving` hooks run. `Receipts.onGranted` reports grants for purchase history or analytics.
- Game passes in `Hydrogen.Receipts`: `owns` (cached per session, updated by in-game purchases), `gamePass` / `gamePasses` handlers that run once per session for owners, `promptProduct` and `promptGamePass`.
- Receipt stores: the `ReceiptStore` interface for recording purchases in the same save as the grant, `Receipts.dataStore()` (the default, one DataStore key per purchase) and `Receipts.memoryStore()` for tests.
- `Receipts.fakeMarketplace()`: a stand-in `MarketplaceService` for tests, with `purchase`, `deliver`, `retryPending`, `buyGamePass` and failure controls.
- `Receipts.fromData(PlayerData)`: a receipt store on a `Hydrogen.Data` player store. Each purchase id is recorded with its grant through `updateOnce`, so a purchase is granted exactly once; handlers get the draft data after the receipt.
- `Hydrogen.Component`: code bound to CollectionService-tagged instances. `Component.new(tag, options)` (or `Component.new(tag, function(use) ... end)`) is a system that, from its `start`, constructs one object with its own scope for every tagged instance in the game, and destroys it (`destroy`, then the scope) when the instance is untagged, destroyed, streamed out or stops passing the filters. Instances tagged before start are bound, and streaming back in constructs a new object. Options: `ancestors`, required `children` (names, or names to classes), a GreenTea `attributes` schema (typed, waited for and kept current), and `timeout` for the missing-children warning. `construct` may yield; an error in one is warned and contained, and it is retried when the instance re-qualifies. Lookups: `get`, `has`, `all`, `instances` and `wait`. `app:stop()` destroys every object. In a game it uses only signals, with no per-frame work; under a fake clock it re-checks on every `t:advance`, so it is testable under Lune and `Hydrogen.test`. Types `Component<I, T>` and `ComponentOptions<I, A, T>`.
- `Hydrogen.Input`: client input actions. Declare `button`, `axis` and `vector2` actions once, with keyboard/mouse, gamepad and touch bindings (single keys, modifier combinations, `up/down/left/right` and `positive/negative` composites, stick axes, triggers, mouse movement and wheel). Actions have `value`, `held`, `onBegan`, `onEnded`, `onChanged` and `onHold`. Contexts (`Input.context`) have a priority and optional sinking, and are toggled with `enable` / `disable` or with counted, scope-tied `enableFor` / `disableFor`. Disabling a context ends its held actions, and buttons are never re-pressed when it comes back. Rebinding (`rebind`, `conflicts`, `unbind`, `resetBindings`) detects conflicts and resolves them by rejecting, swapping, unbinding or allowing. `Input.saveBindings` / `loadBindings` save the changed bindings as plain data, and `captureKey` takes the next key for a "press a key" prompt. Device awareness: `Input.device`, `onDeviceChanged`, per-action `glyph` / `observeGlyph` and a custom `Input.glyphs` provider. Touch: on-screen buttons with `touch = true` (made on first touch), `Input.bindButton` for your own buttons, and `Input.source` for custom controls. `Input.simulate` drives it headlessly, and `Hydrogen.test` resets it between tests. Client-only; built on `UserInputService` (see the README for why not the Input Action System). Types `InputAction<V>`, `InputContext`, `InputDevice`, `InputKey`, `InputBinding`, `InputSavedBindings`, `InputGlyph`, `InputConflict` and `InputSource<V>`.
- The kit modules work together: PlayerState replicates each field through a `Hydrogen.State` per-player value (`State/<name>/<field>`), and its client view reads State live. Data, Scope, State and Receipts read time through `Hydrogen.Clock` and warn through Hydrogen's log, so `Hydrogen.test`'s fake clock and warning capture reach them. `Hydrogen.test` resets State when it closes.
- Tier 2 modules work together: `Hydrogen.Commands`' default permission check asks `Hydrogen.Guards` when the game defined a permission or role with the command's `permission` name (after `admins`, before the Studio rule), and `Guards.invalidate` or defining a role resends command lists. `Hydrogen.Debug`'s default check also lets in players with the Guards permission `"debug"`. Debug's warnings list keeps every warn and error line from `Hydrogen.Log`, the game's loggers included, with its `level` (errors show red in the overlay).
- `Hydrogen.Debug`: network stats and a developer overlay. `Debug.enableStats()` / `disableStats()` / `resetStats()` and `Debug.stats()`, a snapshot per network object: messages in and out (total and per second), estimated bytes, dropped messages (rate-limited, dropped by middleware or failing the schema), and function round-trip and handler times. Stats are a global middleware plus the network's delivery observer; nothing is installed until they are enabled or the overlay asks. Add `Hydrogen.Debug` to the app on both sides for the overlay: F3 (`configure({ key })`) opens a panel with boot timings (`App.new({ debug = true, output = Hydrogen.Debug.bootOutput })`), the server and client network tables, `Hydrogen.State` values, a player's per-player state and inspected Data stores / PlayerStates (`configure({ inspect })`), and recent `[HYDROGEN]` warnings. Server data goes only to authorized players: Studio, the owner of a user-owned game, `configure({ users })`, or your own `configure({ authorize })`. `Debug.fetch(userId?)` reads the same read-only view from client code. Types `DebugOptions`, `NetStat`, `NetLatency`, `DebugView`, `DebugPlayerView`, `DebugRow`, `BootReport`, `DebugWarning`, `DebugInspectable`. `Hydrogen.test` turns Debug stats off when it closes.
- Agent docs: `llms.txt` and `docs/ai/*.md`, one file per API area in a fixed layout, plus `AGENTS.md` for agents working on Hydrogen. They ship in the package.
- `Hydrogen.Log`: tagged, levelled, structured logging. `Log.of(system or name, player?)` returns a logger with `debug`, `info`, `warn` and `error` (logs without throwing), `enabled`, `with(fields)`, `setLevel` and `name`. Lines read `[Shop] bought item=sword price=50`. A system's logger is named after its id, looked up on the first line so it can be made in the constructor. Levels: a global one (debug in Studio, info elsewhere) and per-name overrides with `Log.setLevel(level, target?)` and `Log.level(target?)`. A filtered line costs one comparison; a function message is only called if the line is emitted. Sinks: `Log.console` (the default), `Log.buffer(capacity?)` (a ring buffer for overlays) and `Log.addSink(fn)`; errors in a sink are contained and reported once, and sinks that yield don't hold up the caller. `Log.rateLimit({ burst, window })` drops repeated identical lines and reports how many. Types `Logger`, `LogLevel`, `LogThreshold`, `LogFields`, `LogMessage`, `LogLine`, `LogSink`, `LogBuffer` and `LogRateLimitOptions`.
- Log assertions in the harness: `t:expectLog(level, text)`, `t:logs(level?)` and the `logLevel` test option. Warn and error lines from `Hydrogen.Log` count as warnings for `t:expectWarning` and `t:expectNoWarnings`. The harness puts log levels, sinks and the rate limit back when it closes.
- Character hooks: systems can define `characterAdded(player, character)` and `characterRemoving(player, character)`. They run in dependency order (removal in reverse) on the server and in client apps for every player's character, cover characters that exist at start, respawns and `LoadCharacter`, wait for the player's `playerAdded` hooks, and finish before `playerRemoving` when a player leaves or the app stops. A player's character hooks run one after another, so the old character's `characterRemoving` returns before the new one's `characterAdded`. A character destroyed without `CharacterRemoving`, or streamed out on a client, is removed, and added again if it streams back in. Errors are warned and the other systems still run. Apps with no system defining either hook connect nothing.
- `Hydrogen.Scope.of(system, character)`: a scope per system and character, destroyed right after that system's `characterRemoving`.
- Fake characters in tests: `t:spawnCharacter(player, model?)`, `t:removeCharacter(player)` and `t:streamCharacter(player, streamedIn)` on the harness, and `Hydrogen.Character.spawnFake`, `removeFake` and `streamFake` for a bare `Hydrogen.loopback()`. `t:leave` destroys the player's fake character.
- `Definition.hooks(spec)` (internal, for kit modules): registers a pair of system hooks that apps run with the same guarantees as `playerAdded` / `playerRemoving`, through a per-app feed (`add`, `remove`, `has`, `scope`), with optional parent subjects and per-player callbacks. See "Adding a lifecycle hook" in the README.
- `Hydrogen.Guards`: server-side checks for incoming traffic, attached as middleware. `Guards.cooldown(seconds, { name, charges, gap, group })` makes per-player cooldowns with charges, a minimum gap and shared groups. `:guard()` is the middleware, and `ready`, `use`, `remaining`, `charges` and `reset` work from game code. `Guards.defineRole` and `Guards.definePermission` make a role registry. Its sources are `Guards.userIds`, `Guards.groupRank`, `Guards.gamePass` (through `Receipts.owns`), functions and other roles. Answers are cached per session, with in-flight dedupe and `Guards.invalidate`. `Guards.role` and `Guards.permission` are the guards, and `Guards.hasRole`, `Guards.can` and `Guards.rolesOf` work from game code. `Guards.range(studs, { arg, target, slack })` checks distance to the sender's character, allows latency slack, and rejects NaN and invalid targets. `Guards.inRange` and `Guards.distance` do the same from game code. Also `Guards.check(predicate)`, `Guards.all` and `Guards.any` (cooldowns are used only when everything passes, in one step that can't yield), per-guard `reason` and `onReject`, global `Guards.onReject`, and `Guards.configure({ position, slack })`. A rejected event is dropped, and a rejected function request errors to the client with `[HYDROGEN] <name> request rejected: <reason>`. Cooldown and role state is cleared when a player leaves.
- `tools/create-hydrogen`: `pesde x atk422/create_hydrogen` scaffolds a new game with git, Rojo, Rokit, pesde, Hydrogen, an example system and test, and agent docs.
- `Hydrogen.Signal`: typed signals within one side. `Signal.new<T...>(name?)` with `Connect`, `Once`, `Wait`, `Fire`, `FireDeferred`, `DisconnectAll` and `Destroy`; connections have `Disconnect` and `Connected` and go straight into `scope:add`. `Fire` is immediate and runs listeners in connection order on a reused thread, one thread hop per `Fire`; a listener that yields keeps that thread and the rest carry on. Listener errors are warned with a traceback and don't stop the others. Listeners connected during a `Fire` hear the next one; listeners disconnected during a `Fire` are skipped. Types `Signal<T...>` and `Connection`.
- `Hydrogen.Scheduler`: timers on `Hydrogen.Clock`, so `t:advance` drives them. `after`, `every` (with `jitter`), `fixed` (a fixed-timestep loop with catch-up up to `maxSteps`), `debounce`, `throttle` and `count`. Timers have `cancel`, `pause`, `resume`, `active`, `paused` and `bind(scope)` / `bind(system, player?)` to cancel them with a lifetime. All timers share one min-heap and one waiting `Clock.delay`, so idle timers cost nothing per frame. Callback errors are warned and the timer keeps going; a repeating timer whose last run is still yielded skips runs instead of overlapping. Types `Timer`, `EveryOptions` and `FixedOptions`.
- `Hydrogen.Commands`, an in-game command system. Systems register commands with `Commands.register(name, { args, permission, run, ... })`. Arguments are GreenTea schemas or built-in types (`player` with partial names, `me`, `all` and `others`; `players`, `number`, `integer`, `string`, `boolean`, `enum`, `text`, plus `optional`, `rest`, `named` and custom `arg`). The client sends the raw line; the server rate-limits it, parses it, checks the permission and runs it, and output returns to the caller. Errors name the problem: unknown command (with "did you mean"), bad, missing or extra argument (with usage), no permission. Permissions go through a pluggable resolver (`configure({ permissions })`); the default allows `admins` and everyone in Studio. `Commands.execute(player, text)` runs a line directly and returns the result, for tests and server code. Built-in `help` and `kick`.
- `Hydrogen.Commands.Client`: the client system. It provides a console (F2, or a button on touch screens) with history and autocomplete for command names and arguments. Each command the player may run becomes a `/name` TextChatService chat command, and output also appears in chat while the console is closed. `Client.run`, `Client.output`, `Client.onOutput`, `Client.complete` and `Client.configure({ console = false })` support custom UIs. Commands registers network objects only when its systems are added, so a game without commands pays nothing.
- `Hydrogen.Config`: typed configuration and feature flags, declared once in a shared module with `Config.define(name, { values, flags, segments, environments, source, refresh })`. `Config.value(schema, default)` values are server-only and never replicated; `Config.shared` values are sent to clients. Reads are plain table lookups (`GameConfig.values.RoundLength`), updated in place, with `observe` for changes. Overrides per environment (`studio`, `private`, `reserved`, `live`) and per place id, plus `override` / `clearOverrides` from code on the server. Every declaration and environment table is checked at definition with a `[HYDROGEN]` error.
- Feature flags: `Config.flag(true | false | rule)` with `enabled`, `percent` (deterministic UserId hash, stable as it grows), `users`, `groups`, named `segments` (`users`, `groups` with `minRank`, or a function) and custom `when` checks. Evaluated on the server per player at join (group ranks looked up in parallel, at most 5 s) and again when a rule changes or on `Config.reevaluate(player)`. `flag:enabled(player)`, `flag:observe(player, fn)`, `Config.getFlag(name)` / `findFlag(name)`. Each player's enabled flags replicate to that player only, through `Hydrogen.State`.
- Live config sources: `Config.experienceConfigs()` (Roblox Experience Configs, refreshed on `UpdateAvailable`), `Config.dataStore(name, { key, topic })` (polling plus an optional MessagingService topic) and `Config.memory()` for tests, behind a one-method source interface. Fetched at start and every `refresh` seconds on `Hydrogen.Clock`; each remote value is validated on its own and the last good value kept when one is rejected or a fetch fails. `Config.useEnvironment` and `Config.reset` for tests; `Hydrogen.test` resets Config when it closes.
- Types: `Config<V, F>`, `ConfigSpec<V, F>`, `Flag`, `FlagRule`, `ConfigSegment`, `ConfigEnvironment`, `ConfigSource`, `MemoryConfigSource`.
- Network lint: `pesde x atk422/hydrogen_lint` boots a game's server and client under Lune, each in its own world built from the Rojo sourcemap, and compares what the network registered on each side. It reports one-sided names (with the module, whether clients can see it, and each side's `addNetwork` folders), duplicates (after `Hydrogen.namespace` and `State/<name>`), late registrations (with the line that required the module), kind, schema and `:Encode()` mismatches, `serverFunction`s missing their returns, `clientFunction`s without `gt.args` / `gt.returns`, events nothing listens to, case-only name differences, reserved prefixes, script errors and Hydrogen's boot warnings. Text output with a fix per diagnostic, `--json` for CI and agents, `--strict`, `--ignore`; exit codes 0, 1 and 2. The engine ships in `src/Testing/Lint/` (Lune only, never required by a game); `tools/hydrogen-lint` is the launcher package.

### Changed

- `Hydrogen.logger()` without an `output` option writes through `Hydrogen.Log` (level `info`, tag `HYDROGEN`), so traffic lines reach sinks, buffers and `t:expectLog`. The text is unchanged, and `output` still replaces it.
- Hydrogen's `[HYDROGEN]` warnings go through `Hydrogen.Log` (level `warn`, tag `HYDROGEN`) with their text unchanged, so sinks, levels and rate limiting apply to them.
- A system that's `use`d but wasn't added to the app is now added for you and boots first, at `app:start()` or when a system added later needs it, instead of only warning. `debug = true` prints `[HYDROGEN] Added <Y>: <X> uses it`. A system replaced with `app:replace` doesn't bring its own dependencies. `app:addSystem` after start ignores a system that's already in the app.
- `Scope.of(system, subject)` takes any `Instance` (a player or a character) as its second argument.
- Under the hood, players and characters share one subject lifecycle in the App: removal waits on the hooks it depends on directly instead of polling every frame.
- The network reads time through `Hydrogen.Clock` (the server function timeout, the rate limiter's refill, the batching flush) and warns through an internal log, so tests can fake and capture them. Nothing changes in a game.
- Under loopback, `net:client()` is `nil` while the server handles a client's message. It used to return the sending client.
- Opening a loopback always starts from an empty network, so events an earlier test queued are dropped instead of reaching the new test's clients.
- The test runner runs on the shipped Lune runtime. GreenTea now loads through its own `init`, as in Roblox, instead of the runner loading its inner module directly.

### Fixed

- Harness expectations (`firedBy`, `firedTo`, ...) compare Vector3, CFrame and other value types by value. Under Lune they never matched.
- `app:addNetwork` no longer hangs on a module that returns a `Hydrogen.State` object, a GreenTea schema or anything holding one. The object count walked tables with a generic `for`, which calls a table that has `__call` as its iterator, forever.
- `State.reset()` (and so `Hydrogen.test` closing) no longer leaves State unable to replicate when a test ended before its end-of-frame send ran.
- `Hydrogen.rateLimit` no longer locks a player out when the clock it reads moves backwards (e.g. a bucket made before a test's fake clock was installed).

## 0.4.0

### Added

- Player and shutdown hooks: systems can define `playerAdded`, `playerRemoving` and `stop`. `playerAdded` runs in dependency order; `playerRemoving` and `stop` run in reverse, so a system runs before the systems it `use`s. `playerRemoving` waits for that player's `playerAdded` hooks to finish, and an error in one system's hook is reported without skipping the others.
- `app:stop()`: runs `playerRemoving` for players still in the game, waits for every `playerRemoving` hook, then runs `stop` hooks. Bound to `game:BindToClose` on the server.
- `Hydrogen.namespace(prefix)` and the `Namespace` type: constructors that prefix network names with `prefix/`, so places sharing code can reuse names. Namespaces nest with `namespace.namespace(...)`.
- `app:addNetwork` and `app:addSystemsFolders` warn when they find nothing to register.
- Network mismatch detection: the client sends a fingerprint of its sorted network names in the ready handshake, and both sides warn `[HYDROGEN] NETWORK MISMATCH` when it differs from the server's.
- `serverFunction:SetTimeout(seconds)`. `Fire` errors when the client hasn't answered in time.
- `Hydrogen.rateLimit(options)`: a middleware that drops a player's incoming messages beyond `perSecond` (with `burst` and `onLimit` options), per network object.
- `Hydrogen.DROP`: a middleware can return it to stop a message. Dropped events are not delivered; dropped function payloads error.
- `event:Unreliable()` on server and client events, which sends over an `UnreliableRemoteEvent`. Unreliable events are never queued.
- `Hydrogen.define(id, constructor)`, for an explicit id instead of the calling module's name.
- `App.new({ debug = true })` prints how long each system's `init` and `start` took. `output` changes where it goes.
- `app:replace(original, fake)`: before `start`, swap a system for a fake. The fake's hooks run in the original's place in the boot order, and while the app runs the original table forwards reads and writes to the fake, so dependents that already hold it reach the fake. `app:stop()` (or a failed boot) restores the original.
- `Hydrogen.loopback()` and the `Loopback` type: in-memory remotes and fake players, so one VM can run server and client systems together in a headless test. Messages still go through middleware, validation and the ready handshake. `join`, `leave`, `as` and `client` control the fake clients; `close` removes listeners and middleware added since it opened and stops the network for the next test.
- README section "Testing your systems", including why `replace` redirects the original rather than having `use` return a proxy.
- `App.new({ batching = true })`: events fired during a frame are collected per target and sent on `Heartbeat` as one remote call per target. They are dispatched in order on the receiving side. Reliable and unreliable events batch separately, and unreliable batches are split to stay under an estimated 900 bytes. Calling a function sends that target's pending events first. Skipped under `Hydrogen.loopback()`. Off by default.
- `:Encode()` on all four network object kinds: payloads are packed into a `buffer` using the GreenTea schema (numbers, with 1, 2 or 4-byte integers when an integer range allows it; strings; booleans; `Vector3`; `CFrame`; buffers; arrays; tables; dictionaries; optionals; literals; tuples and varargs). Types it can't pack travel as plain values beside the buffer. Validation still runs on the decoded values, and middleware sees plain values. Off by default.

### Changed

- **Breaking:** registering a network name twice errors. It used to warn and keep the first object, so the second module silently talked to the wrong one.
- `app:addNetwork` takes several instances, like `addSystemsFolders`. Given a ModuleScript, both now require the module itself as well as its descendants. Previously a ModuleScript on its own registered nothing.
- `app:addNetwork` and `app:addSystemsFolders` accept any `Instance`, so `WaitForChild` results need no cast.
- Dependency warnings and cycle errors name systems by their module's full name, and carry the `[HYDROGEN]` prefix.
- **Breaking:** `serverFunction:Fire` times out after 10 seconds by default instead of waiting forever. Use `:SetTimeout(math.huge)` for the old behaviour.
- An error in a system's `init` or `start` is reported as `[HYDROGEN] System <name> failed in <hook>: ...` with the traceback. Boot still stops at the first error.
- The server also creates `ReplicatedStorage.HydrogenNetworkUnreliableRemoteEvent`, and the ready handshake now carries the names fingerprint. Server and client must run the same Hydrogen version.
- The README states that Hydrogen supports one app per side.
- Network id `0` on the event remotes now marks a batch, so a receiver understands batches whether or not its own app batches.
- The test runner exits explicitly once the suites finish, so a test that leaves a thread waiting can't keep Lune running.

### Fixed

- Events sent to a player who has left are dropped. Before, a send after Hydrogen's `PlayerRemoving` handler ran (after a yield, or from a later handler) created a queue for that player that was never cleared.

## 0.3.0

### Added

- Network middleware. Per object with `event:Use`, `fn:UseRequest` and `fn:UseResponse`; for every object with `Hydrogen.useMiddleware`. Each returns a function that removes the middleware.
- `Hydrogen.logger(options?)`, a middleware that logs network traffic for debugging, with `filter` and `output` options.
- `Hydrogen.gt`, the GreenTea instance Hydrogen validates with.

### Changed

- **Breaking:** incoming event payloads are validated against the schema on the receiving side. Invalid payloads (including anything a client sends to the server) are dropped with a warning instead of reaching listeners.
- **Breaking:** calling `clientFunction:Fire` or `serverFunction:Fire` before the network starts now errors with a clear message. Previously it sent the reserved handshake id.
- **Breaking:** the unused `_outgoingMiddleware` and `_incomingMiddleware` fields are replaced by `_middleware` (events) and `_requestMiddleware` / `_responseMiddleware` (functions).
- The type of `clientEvent:On` now includes the sending `player` as the listener's first argument, matching what it receives at runtime.
- Events with an unknown network id are dropped with a warning instead of erroring.
- The development Rojo project now mirrors the layout pesde generates for consumers (`src` and `roblox_packages` side by side), so network modules resolve GreenTea in Studio.
